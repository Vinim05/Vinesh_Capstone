# PolyPredict Ethics Statement

**Team members:** Vinesh Murikinati and Charlie Crocker  
**Project:** PolyPredict — Prediction Market Sentiment Trading System  
**Date:** November 11, 2026  
**Status:** Design-stage statement. Implementation and required security tests are not yet complete.

PolyPredict is a locally hosted, paper-trading-only capstone system. It collects publicly available prediction-market and news information, detects market changes, uses a local Qwen model to produce analysis, and displays trading signals and simulated results. This statement applies the ACM Code of Ethics principles of avoiding harm, respecting privacy, being honest about system limitations, and giving appropriate credit. It expands the Ethical, Legal, Security, and Diversity and Cultural constraints discussed in `Constraints_Essay.md`. References to planned protections below are commitments for implementation, not claims that those controls have already passed testing.

## 1. Privacy Summary

PolyPredict will not ask for or store user names, email addresses, account passwords, brokerage credentials, or other personal profiles. Its only intended operators are the two student developers, Vinesh and Charlie. Market and news data are obtained from external public sources, not from people entering personal information into the dashboard. A public article can still contain a person's name, so the system will limit retained news data to what is needed for market analysis and will not build profiles of individuals.

The table covers the planned data that moves between the Collector, Shift Detector, AI Engine, Signal Generator, SQLite Storage, Paper Trading component, and Dashboard in the D0–D2 design. Field-level naming must be reconciled against the final Week 9 schema before release.

| Data item / fields or field groups | Source | Purpose | Consent / collection basis | Storage and access | Retention / end-of-project action |
|---|---|---|---|---|---|
| Market event identifiers, titles, outcomes, status, and market metadata (`MarketEvent`) | Public Polymarket API | Identify and describe tracked markets | Public API data; follow provider terms, no user consent requested | Local SQLite; accessed by local pipeline and dashboard | Keep only selected non-sensitive demo records; delete other local records |
| Market prices, probabilities, volume, timestamps, and observed changes (`MarketObservation`) | Public Polymarket API | Measure probability shifts and compare observations | Public API data; follow source terms | Local SQLite; pipeline and local dashboard | Keep a small demo sample; delete remaining observations |
| Article identifiers/URLs, titles or summaries, source, publication times, and relevant content (`NewsItem`) | Public news feeds or APIs, to be chosen | Give market movement context | Public or provider-authorized content; respect access and reuse limits | Local SQLite if needed; local analysis pipeline | Retain only permitted short demo references/summaries; delete other content; avoid unnecessary personal details |
| Shift scores, affected market references, comparison windows, and trigger times | Collector / Shift Detector outputs | Explain why analysis was triggered | Derived from the above data; no separate consent | Local processing and SQLite as required | Keep selected demo outputs; delete remaining records |
| AI analysis text, confidence or rationale, related market/news references, and timestamps (`AnalysisResult`) | Local Qwen3.5 9B inference | Interpret a shift and support an explainable signal | Derived processing of source data; no additional personal data intended | Local inference; stored in SQLite for display/review | Keep sanitized demo examples; delete other analyses |

| Run IDs, component status, timing, error messages, and validation/failure counts (`SystemRun` and application logs) | Local application components | Debug failures and measure reliability | Generated by project operation; no user tracking intended | Local logs/SQLite, developer-only access | Delete operational logs after the project; keep only anonymized demo run summaries |
| API configuration, optional API tokens, and model configuration | Student developers / providers | Configure access to external data and local inference | Developer-controlled credentials; not collected from users | Local `.env`, excluded from Git; never copied into SQLite, logs, or screenshots | Delete or revoke unused secrets at project end; do not keep credentials in demo data |

**Consent and minimization:** There is no sign-up flow because the only intended users are the two developers, who operate their own local installation. The README and dashboard should disclose the public data sources, local storage, and paper-trading-only scope before use. If the project is later opened to testers or collects user-provided information, the team must add a clear consent notice and update this table first. No personal-data field has been removed from an implemented schema; registration, email, and brokerage-account fields were excluded from the design because the project does not need them.

**Retention mechanism (planned):** After final demonstrations, the team will export a small reviewed SQLite demonstration dataset, remove unnecessary news text and personal references, delete other working databases and log files locally, and revoke unused credentials. The project currently has no automated deletion job; completion of this manual cleanup must be documented in the final report. Backups or copied databases must be included in that review.

## 2. Security Summary

PolyPredict has no public accounts, no default usernames or passwords, and no login or API authentication in its planned local-only configuration. **Unauthenticated endpoints are an intentional limitation, not a general security solution.** The FastAPI server and dashboard must bind to `127.0.0.1` rather than `0.0.0.0`; port forwarding, public tunnels, and public hosting are outside the approved scope. Requests must validate inputs, and operations that could execute commands or expose arbitrary local files must not be provided. Only paper trades are allowed; no real-money orders are supported.

| Control | Project approach / status |
|---|---|
| Default credentials | None designed; no preconfigured administrator account |
| Authentication method / token lifetime | No user authentication or session tokens for localhost-only use; therefore no token lifetime applies |
| Unauthenticated endpoints | Local-only access is the primary boundary; confirm binding and test access from another device before demonstration |
| Secrets in source control | `.env` is **assumed to be listed in `.gitignore`** as requested; this has not been verified in the implementation. Commit an `.env.example` with placeholder values only |
| Git history secret scan | **Not yet run. Result: pending, not “clean.”** Scan all commits before submission and rotate/revoke any exposed secrets if found |
| HTTPS | Not configured for loopback HTTP; if made remotely accessible, require HTTPS, authentication, and a revised security review |
| Rate limiting | No application-level limit confirmed. Limit outgoing polling to provider rules and add local endpoint throttling if abuse or accidental overload becomes a concern |
| Storage permissions | SQLite and `.env` files should be readable only by the local developer account; never serve the database as a static file |
| Failure handling | Validate API responses, time out external calls, log errors without tokens, and skip unreliable signals rather than making unsupported trades |

**Required pre-submission audit:** Run `git check-ignore -v .env` (after creating `.gitignore`) and `git ls-files --cached | grep -E '(^|/)\.env($|\.)'` to check tracking. Run a full-history secret scanner such as Gitleaks with `gitleaks git --repo-path .` or the syntax required by its installed version, and record its date and results. Confirm the web server is bound to loopback and test that another machine cannot reach it. These commands have **not** been executed for this statement.

| Self-audit question | Answer |
|---|---|
| Are default credentials installed? | No accounts or default credentials are planned |
| Can unauthenticated users call the API? | Yes, from the local machine; remote access must be blocked by loopback binding |
| Are API keys committed to Git? | `.env` is assumed ignored; current files and complete Git history are not yet audited |
| Is the application publicly reachable? | Not intended; localhost only, pending network verification |
| Can it execute real-money trades? | No; simulated paper trades only |
| Are data and model outputs guaranteed correct? | No; signals are research outputs and must not be treated as financial advice |
